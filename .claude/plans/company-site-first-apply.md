# Company-site-first apply (plus email channel)

## Context
Sean wants the company's own site to be the main way a CV reaches them (a posting on their careers site, a general "send us your CV" form, or a published jobs/HR email), with LinkedIn/AllJobs/JobMaster as the fallback. Research today returns only `website`, `tldr`, `careers_url`, and `apply.py` tries exactly one URL. MX for larch-networks.com is Google Workspace (aspmx.l.google.com), so SMTP is `smtp.gmail.com:587` STARTTLS with a Google App Password.

## Design

### Research output (autojob/llm/research.py)
`research_company(company_name, job_title, *, work_dir, job_url="")` (new optional kwarg: the board posting URL, so the model knows which posting to look for). Prompt asks for ONLY a JSON object with: `website`, `tldr`, `careers_url`, `job_url_on_company_site`, `general_cv_url`, `cv_email`, `cv_email_source_url`. Prompt rules, stated verbatim to the model: every URL returned must be a page it actually fetched with WebFetch; `job_url_on_company_site` is this posting on the company's own site or on its ATS (Comeet, Greenhouse, Lever, etc.) linked from the company site, never a job board; `cv_email` must be an address literally seen on a fetched page, with that page as `cv_email_source_url`, and it must never be guessed from a pattern like jobs@domain. Profile line replaces the "about 2 years" sentence with a `SEAN_PROFILE` constant in research.py: junior penetration tester, HTB CPTS, TCM PNPT, eJPT, 100+ HTB/THM machines, home AD lab, close to no professional pentest experience.

Python validation (pure functions, unit-tested): `_clean_url(value)` keeps only `http(s)://` strings, and drops any URL whose host is a job board (`linkedin.com`, `alljobs.co.il`, `jobmaster.co.il`, `drushim.co.il`, `indeed.com`, `glassdoor.com`); `_clean_email(email, source_url)` lowercases, requires `^[^@\s]+@[^@\s]+\.[^@\s]+$`, and returns `(None, None)` when `source_url` fails `_clean_url`. Return dict always has all 7 keys; the fail-soft branch returns `tldr="unknown (...)"` and None for the rest.

### Storage (autojob/db.py)
Decision: `job_url_on_company_site` is per posting, so it lives on `jobs.company_site_url`; the three company-level facts live on `companies`. Research is still one call per company (the first queued job of that company supplies title and URL); a second queued job at the same company simply has no `company_site_url` and starts at channel (b).
- companies: `general_cv_url TEXT`, `cv_email TEXT`, `cv_email_source_url TEXT`, `channels_researched_at TEXT` (stamped on every research write, even when everything came back null, so re-research is bounded).
- jobs: `company_site_url TEXT`.
- applications: `email_to TEXT`, `email_draft TEXT` (JSON: to, subject, body, attachment_name); channel CHECK gains `OR channel LIKE 'email:%'`. Channel value is `email:<address domain>` (`email:acme.com`).
- Settings key `email_daily_cap` (int, default 15), edited on the Targets page.
- SMTP credentials: `data/smtp.json` (0600) with `host`, `port`, `username`, `password`, `from_address`; `Config.smtp_path` property.

### Channel order (autojob/apply/apply.py, `plan_channels(job, conn) -> list[tuple[kind, target]]`)
(a) `company_job`: `jobs.company_site_url`. (b) `careers`: `company_careers_url` only when `_careers_url_looks_like_a_posting(url)`: `pick_handler_by_url(url)` recognizes it, or the path has 2+ segments and the last segment contains a digit or is 12+ characters (a slug); a bare `/careers` listing is skipped. (c) `general_cv`: `company_general_cv_url`. (d) `email`: `company_cv_email`, dropped from the plan when `db.email_already_sent` for this job+address or the daily email cap is reached (event logged; the job continues to (e) today, see Q1). (e) `job_url`: `job["url"]`. Duplicate targets are removed keeping the first. Everything before (e) is a "company" channel. A fresh account with no research sees exactly today's behaviour: only (e).

Fall-through rule (`_should_fall_through(result, is_last)`): a `needs_help` or `failed` result on a non-final channel falls through when the reason contains one of `FALL_THROUGH_MARKERS = ("CAPTCHA", "Could not locate", "Could not find a submit control", "Could not open", "Account signup required", "unexpected error", "Apply handler raised", "before a form could be filled")`, or when `page.goto` raised. Any other `needs_help` (a required question the handler can't honestly answer, a login requirement) escalates immediately: the form is usable and only Sean's answer is missing, and skipping the company form for a lesser channel would defeat the point. On the final channel nothing falls through (today's behaviour). `sent` / `ready_to_submit` end the chain.

One application row per `apply_to_job` call: cover letter and screening answers are generated once before the loop (`generate_application_content`, unchanged); the row is created with the first channel and `db.update_application(channel=, apply_url=)` is called at the start of every attempt, so `applications.channel` always records the channel that ended the chain. Fallen-through attempts append `Tried <kind> <target>: <reason>` lines to `notes` and save their screenshot as `attempt-<n>-<kind>.png` (kind `screenshot`); the terminal attempt keeps `form.png`. The browser is opened once around the loop; the email channel runs inside it without touching the page.

### Email channel (autojob/apply/mailer.py, new)
No second LLM call: the email body is the already-generated cover letter (same honesty rules, same text Sean reviews on the detail page) followed by a contact block from `profile.answers` (`email`, `phone`, `linkedin_url`, only those set). Subject: `Application for <job title> (<full_name>)`. Attachment: newest CV PDF (`latest_cv_pdf`) with its own filename, or none if no CV is uploaded. Draft dict: `{"to", "subject", "body", "attachment_name"}` stored in `applications.email_draft` and `email_to`.
- `auto_submit` off: draft stored, application `ready_to_submit`, job `applying`. Detail page shows the draft; Release sends it, Discard works as today.
- `auto_submit` on: send immediately; `sent` + proofs, job `applied`.
- SMTP not configured, auth or connection failure: application stays `ready_to_submit` with the draft, plus a help item `Email SMTP not configured. Run: uv run python -m autojob.set_smtp` (or `Email send failed: <reason>`), job `needs_help`. A later Release retries; on success open help items for the job are resolved with `Email sent on release.` Terminal: never falls through to (e).
- Proof: `sent.eml` (exact bytes sent, `msg.as_bytes()`) and `sent_email.txt` (From/To/Subject/Date/Attachment header block plus body), both proof kind `sent_email`. Daily cap counts `COUNT(DISTINCT application_id)` of `sent_email` proofs since local midnight.
- `set_smtp` CLI (`autojob/set_smtp.py`, modeled on set_password.py): prompts host (default smtp.gmail.com), port (587), username (default sean@larch-networks.com), from address (default = username), password via getpass, writes smtp.json 0600, prints a reminder that Google Workspace needs an App Password (2-step verification on), then offers a test email to the from address (y/N).
- Targets page shows `SMTP: configured as <from_address>` or `SMTP: not configured (run uv run python -m autojob.set_smtp)` under a new "Daily email cap" number input. Nothing else for Sean to type; the addresses come from research.

### Re-research (autojob/pipeline/research.py, new)
`research_pending(conn, *, work_dir, limit, run_id=None, logger=None) -> int`: `db.list_queued_jobs_needing_research(conn, limit)` returns one queued job per company whose `channels_researched_at IS NULL` (companies with an old tldr but no channel research included), newest first; for each: `research_company(..., job_url=job["url"])`, `db.update_company_research(...)`, `db.set_job_company_site_url(job_id, url)`, events as today. `run_scan` replaces its inline research loop with this call (same cap, same events, same failed count), so existing companies get the new fields hands-off on the next run. Jobs page (Queued tab) gets a button `Research companies for direct apply channels` (POST `/jobs/research-pending`, background thread holding `app.state.run_lock`, redirect to `/jobs?status=queued&research=started`, flash `Research started in the background.`; `?busy=1` when the lock is held). Also `uv run python -m autojob.pipeline.research`. Queued rows show a `Direct` cell: `site` / `form` / `email` / `-` from the joined columns, so Sean can see what research found.

### Dashboard
application_detail.html: when `application.email_draft` is set, a card `Email` (To, Subject, Attachment, Body pre-wrap) above Proofs; Release button reads `Release (send email)` for `email:` channels. targets.html: cap input and SMTP line as above.

## Risks
- Research quality: sonnet may still return an unfetched URL; validation only catches boards and bad formats. Watch the first few `company_site_url` values.
- Google may reject the App Password login if 2-step verification is off; the help item then says so and Release retries.
- `research_pending` replaces the inline loop in `run_scan`; behaviour change is limited to re-researching companies with a tldr but no stamp (bounded by the cap).
- Mailing from the employer's Workspace mailbox is visible to that Workspace's admins (Q1).
